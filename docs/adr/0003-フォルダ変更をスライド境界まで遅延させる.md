# ADR 0003: フォルダ変更をスライド境界まで遅延させる

- 状態: 有効
- 日付: 2026-08（MVP 開発時の判断を後追いで記録）

## 文脈

監視フォルダにファイルが追加・削除されたら表示に反映する必要がある。`FileSystemWatcher` は変更を即座に通知してくるが、通知のタイミングは利用者の操作（エクスプローラーでのコピー）に完全に従属する。

素直に「通知を受けたら即リロード」と書くと、掲示を見ている人の目の前でスライドが突然切り替わる。さらに、大きなファイルのコピー中は `Changed` が何度も飛ぶため、リロードが連続する。

## 決定

`ContentFolderWatcher.ContentChanged` を受け取ったら `_playlistReloadPending = true` を立てるだけにして、実際の再構築は次のスライド送りのタイミング（`AdvanceToNextSlide()` の先頭）で行う。

## 理由

- **表示中のスライドを絶対に中断しない。** サイネージとして、読んでいる途中の掲示が消えるのが最も体験を損なう
- 複数の変更通知が来ても、pending フラグが立つだけなので自然に合流する（デバウンス相当の効果）
- コピー途中のファイルは、次のスライド境界までに完了している可能性が高い。読めなければ従来どおりスキップされる

## 検討した代替案

**即時リロード** — 実装は最も簡単だが、表示中断が起きる。却下。

**タイマーによるデバウンス（例: 最後の通知から 2 秒後にリロード）** — 連続通知は抑えられるが、表示中断の問題は解決しない。スライド境界という自然な区切りが既にあるのに、別の時間軸を持ち込む理由がない。

**ファイルのロック状態を見てコピー完了を判定する** — 判定が環境依存で信頼できない。読めなければスキップする既存の仕組みで十分と判断。

## 結果

**「ファイルを置いてもすぐ変わらない」が仕様になる。** 特に長い動画を再生中は、再生完了まで反映されない。これは利用者から見ると不具合に見えるため、[操作ガイド](../操作ガイド.md)と[運用ガイド](../運用ガイド.md)の両方で明示的に説明している。**この挙動を変えるなら、両ドキュメントも直すこと。**

再構築後の再生位置を保つために `MainViewModel.ResolveIndexAfterReload()` が必要になった。「次に表示するはずだったスライド」を手がかりに新しいリスト内の位置を探す処理で、これ自体はやや複雑。ここを単純化すると、コンテンツを 1 つ差し替えるたびに先頭へ巻き戻る挙動になる。

コンテンツが 0 件のときは `FileSystemWatcher` の通知だけに頼らず、デフォルト表示秒数間隔のポーリングで再スキャンしている（`MainViewModel.OnTimerTick`）。監視が取りこぼしても必ず復帰させるための二重化。
