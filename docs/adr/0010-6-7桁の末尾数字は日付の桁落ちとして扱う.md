# ADR 0010: 6〜7 桁の末尾数字は日付の桁落ちとして扱う

- 状態: 有効
- 日付: 2026-09-12
- 関連: [ADR 0009](0009-ファイル名の再生期限と入力誤りはキオスクを止めない.md) の桁数ルールを一部改訂

## 文脈

ADR 0009 では「4〜7 桁・9 桁以上の末尾数字はメタデータではないので無視する」としていた。現場で `_2026923`（月の 0 抜けで 7 桁）のような名前が置かれ、期限指定のつもりでもアラートも期限解釈もされず、気づきにくいことが分かった。

## 決定

- **6〜7 桁**の末尾 `_数字` は、8 桁日付（`YYYYMMDD`）の桁落ちとして**入力誤り**にする（期限なしで再生は続ける）
- **4〜5 桁**（`IMG_2716`、西暦年 `2024` など）と **9 桁以上**は、これまでどおり無視する（誤りにもしない）
- 管理モードの MessageBox 本文は、個別理由の列挙ではなく、次の案内＋対象ファイル名とする  
  「このファイルの表示期限の指定方法があやっていますのでファイル名を修正してください。」  
  「例）○○_20261231、○○_20_20260212」

## 理由

- `_20260923` のつもりで `_2026923` と書く誤りは現実に起きる。8 桁に近い長さなので「期限の typo」と判断しやすい
- 4 桁のカメラ番号や西暦年まで誤りにすると誤報が増える
- MessageBox は管理者がすぐ直せるよう、正しい形の例を先に見せる方が実務向き

## 検討した代替案

**7 桁だけ誤り、6 桁は無視** — `YYYYMMD` と `YYMMDD` の区別が説明しづらい。6〜7 をまとめた。

**4〜7 桁すべて誤り** — `IMG_2716` が誤報になる。ADR 0009 で却下した問題が戻る。

**MessageBox にパーサーの詳細理由を列挙し続ける** — 技術的には正確だが、現場向けの直し方が伝わりにくい。

## 結果

`DisplayDurationParser.IsMetadataCandidate` が 6〜7 桁も含め、`ClassifyTokens` で誤りメッセージを付ける。`FormatIssuesMessage` は案内文＋ファイル名のみ。ADR 0009 の「再生は止めない」「管理モード入場時に知らせる」は維持する。
