# ADR 0002: DI コンテナを使わない

- 状態: 有効
- 日付: 2026-08（MVP 開発時の判断を後追いで記録）

## 文脈

設定・ロガー・解決済みパスをアプリ全体で共有する必要がある。WPF の一般的な構成では `Microsoft.Extensions.DependencyInjection` などを `App.xaml.cs` で組み立てる。

## 決定

DI コンテナを導入せず、`ApplicationContext` という静的シングルトン（`ApplicationContext.Current`）に共有物をまとめる。各 Window / ViewModel はこれを直接参照するか、コンストラクタで受け取る。

## 理由

- 共有する依存が実質 5 つ（`Settings` `ResolvedWatchFolder` `LogDirectory` `Logger` `SettingsService`）しかなく、コンテナを入れても記述量が減らない
- 起動シーケンスが「設定を読む → パスを解決する → ロガーを作る」という一本道で、依存の解決順序に自由度がない。コンテナの利点である遅延解決が効かない
- ウィンドウが 2 つ（キオスク・管理）だけの単一プロセスアプリで、スコープ管理が不要

## 検討した代替案

**Microsoft.Extensions.DependencyInjection を使う** — 標準的で将来の拡張に強いが、この規模では `ServiceCollection` の記述が純粋な追加コストになる。

**すべてコンストラクタ注入で手渡しする** — テスト容易性は最も高いが、`MainWindow` → `MainViewModel` → 各サービスへ 5 つの依存を延々と渡すことになり、キオスクアプリの実態に対して煩雑。

## 結果

**`ApplicationContext` に依存するクラスは単体テストが実質できない。** `MainViewModel` `AdminViewModel` `ScheduleService` がこれに該当する。

その代わりに、テストしたいロジックは `ApplicationContext` を参照しない静的クラスへ切り出す方針を採っている（`DisplayDurationParser` `NaturalStringComparer` `ScheduleTimeHelper` `SettingsValidator` `PathHelper`）。**新しいロジックを足すときは、まずこの層に置けないかを検討すること。** ここに置ければ `PdfSignage.Tests` でカバーできる。

ViewModel のテストが本当に必要になったら、そのときが DI コンテナ導入を再検討するタイミング。
