# ADR 0001: PDF レンダリングに Docnet.Core を採用する

- 状態: 有効
- 日付: 2026-08（MVP 開発時の判断を後追いで記録）

## 文脈

PDF を 1 ページ = 1 スライドとして全画面表示する必要がある。WPF には PDF の描画機能がなく、外部ライブラリが要る。配布はポータブル（インストーラーなし）で、現場 PC に別途ソフトを入れさせない前提。

## 決定

`Docnet.Core`（PDFium の .NET ラッパー）を使い、ページを BGRA のビットマップにラスタライズして `BitmapSource` へ変換する。

## 理由

- PDFium は Chrome の PDF エンジンで、実務で使われる PDF の描画品質が信頼できる
- NuGet パッケージにネイティブバイナリが同梱されるため、現場 PC への追加インストールが不要
- ライセンスが商用利用の妨げにならない（PDFium は BSD-3-Clause）
- ページ単位のラスタライズという、こちらが必要とする最小の機能だけを提供している

## 検討した代替案

**Adobe Acrobat / Reader の COM 連携** — 現場 PC への Acrobat インストールが前提になる。ポータブル配布という要件と両立しない。

**WebView2 で PDF を表示** — Edge の PDF ビューアが出るため、ツールバーやスクロールバーの抑制に苦労する。キオスク表示との相性が悪い。また WebView2 ランタイムの配布が必要。

**PDF を事前に画像へ変換して運用する** — コンテンツ担当者に変換作業を強いる。「フォルダに置くだけ」という中心的な要件に反する。

**商用 PDF ライブラリ** — 機能過剰かつライセンス費用が見合わない。

## 結果

ネイティブ依存が入るため、ターゲットは `win-x64` に固定される（`RuntimeIdentifier` 指定、`IncludeNativeLibrariesForSelfExtract=true`）。ARM 版 Windows は対象外。

PDF のページ描画は同期的で、大きなページでは時間がかかる。これを吸収するために `SlidePreloader` で次スライドを先読みし、`PdfRenderer` が `IDocReader` をキャッシュする構成になっている。**Docnet を差し替えるなら、この 2 つの存在理由も一緒に再検討すること。**
