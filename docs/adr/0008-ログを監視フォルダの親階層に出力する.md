# ADR 0008: ログを監視フォルダの親階層に出力する

- 状態: 有効
- 日付: 2026-08（MVP 開発時の判断を後追いで記録）

## 文脈

エラーログの出力先を決める必要がある。候補は exe と同じフォルダ、`%LOCALAPPDATA%`、監視フォルダの中、監視フォルダの親。

障害時にログを確認するのは現場のシステム管理者で、開発者ではない。「どこを見ればいいか」を電話越しでも説明できることが重要。

## 決定

監視フォルダと**同じ階層**（親フォルダ）に `logs` フォルダを作る。`D:\Signage` が監視フォルダなら `D:\logs`。ファイル名は `app_yyyyMMdd.log` の日次で、7 日を超えたものは起動時と監視フォルダ変更時に自動削除する。

## 理由

- 管理者が既に知っている場所（監視フォルダ）を起点に説明できる。「コンテンツを置いているフォルダの、ひとつ上に logs があります」で通じる
- **監視フォルダの中に置かない**のが要点。`logs` フォルダを監視対象の直下に作ると、`FileSystemWatcher` が自分のログ書き込みに反応しかねず、コンテンツ一覧にも異物が混ざる
- 監視フォルダを変えたらログ出力先も追従するため、「コンテンツとログがセットで移動する」という直感に合う
- 7 日保持は、無人運転で容量を食い潰さないための上限。障害調査には十分な期間

## 検討した代替案

**exe と同じフォルダ** — 配布フォルダが `C:\Program Files` 配下だと書き込めない。また設定ファイルと違い、ログは日々増えるので配布物の場所に置きたくない。

**`%LOCALAPPDATA%\PdfSignage\logs`** — Windows の作法としては正しいが、現場の管理者にパスを説明しづらい。エクスプローラーのアドレスバーに環境変数を打つ操作を要求することになる。

**監視フォルダの直下（`D:\Signage\logs`）** — 上記のとおり `FileSystemWatcher` とコンテンツ一覧を汚す。

## 結果

**ログフォルダには書き込み権限が要る。** 監視フォルダが読み取り専用の共有フォルダだと、親に書き込めず失敗する。UNC パス運用を正式サポートする際は、ここが最初の課題になる。

`PathHelper.ResolveLogDirectory()` に分岐が増えた。設定上のドライブ（例: `D:`）が存在しない開発 PC では、実際に解決された監視フォルダ（`{exe}/SignageData`）を基準にログ先を決める。開発時に `D:` が無くても動かすための妥協。

監視フォルダを変更したときは `ApplicationContext.ApplySettings()` → `FileLogger.SetLogDirectory()` で出力先を切り替える。**切り替え時にも期限切れログの削除が走る。**
